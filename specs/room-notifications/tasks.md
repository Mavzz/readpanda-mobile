- Task 1: two additions to design.md. An index on `notifications (user_id, updated_at DESC)`, since the inbox will sort on `updated_at` (task 9). And `ENABLE ROW LEVEL SECURITY` on `notification_settings` in the migration: `readpanda_schema.sql` turns RLS on for every table when built fresh, but a table the migration creates on Supabase would otherwise be readable through the anon REST API. The unique index uses `is_read IS NOT TRUE` because `is_read` is nullable, so task 5's `ON CONFLICT` must repeat that predicate exactly. The first run copies `created_at` into `updated_at` so existing rows keep their order. Checked: run three times on a database built from the previous schema, the result matches a fresh `readpanda_schema.sql` load for both tables, the upsert keeps one unread row and starts a new one after read, and room and user deletes cascade. Applied to the local dev DB. Backend work is on branch `feat/room-notifications` (from `develop/1.1.0`).
- Task 2: the switch filter is `switchedOn(type, userExpr)`, a `NOT EXISTS` on `notification_settings` that recipient queries add to their WHERE; SYSTEM has no switch and gets `TRUE`. Reading one reader's settings for `GET` is left to task 3. `models.Notification` gains `room_id`, `count` and `updated_at`, which `GetUserNotifications` fills in task 9. The window is `Config.RoomCommentWindow` via `getDurationEnv`; a value that doesn't parse or isn't positive is logged and 30m used. Tests: `internal/notify/settings_test.go` runs each type's condition against real rows (no settings row, one switch off, all off); `internal/config/config_test.go` covers the duration parsing.
- Task 3: `notify.LoadSettings` / `notify.UpdateSettings` (one upsert with `COALESCE`, so the first change creates the row with the other switches on). Two additions to design.md: `PUT` rejects unknown keys with 400, so a misspelt switch isn't a silent no-op that still answers 200; and a valid token for a deleted account gets 404 on `PUT` (`GET` still answers the defaults). `internal/server/notifications_test.go` is created here with the settings tests (defaults, subset updates and read-back, per-user isolation, bad bodies, 401, deleted account); task 10 adds the delivery tests to it. `ROUTES.md` already describes the switches as stopping the inbox row and the push, which is true once task 4 lands.
- Task 4: `ToUsers` is removed: nothing called it, and `Send` replaces it. `Send` dedupes its recipients (`SELECT DISTINCT`), so a caller listing someone twice still writes one row. When the 5s timeout hits, the loop stops trying the remaining devices instead of logging a failure for each one. `ToAllUsersExcept` keeps its background push (2 min bound) and now skips readers with New books off. `sendPush` and `pushTimeout` are package vars so tests can fake FCM and shorten the timeout. Tests: `internal/notify/notify_test.go` (pushed before `Send` returns, data carries `room_id` / `room_name` and omits empty ones, one row per user, switched-off readers get no row or push but other types still reach them, timeout doesn't fail `Send` and the rows stay, stale tokens removed, push disabled still writes the inbox, broadcast skips New books off) and `internal/utils/push_test.go` (the request to a stand-in FCM has `apns.payload.aps.sound = "default"`). All pass under `-race`, as CI runs them.
- Task 5: page numbering confirmed: `book_comments.page` is a 0-based index and the reader shows `page + 1` (`CommentSheetView.swift` stamps "p. \(comment.page + 1)", "waiting at p." adds 1), so the locked text is `p. {page + 1}`. The lock rule is the comment layer's: unlocked when `page <= furthest_page`, no progress row = 0. `RoomComment` is one `INSERT … ON CONFLICT` on the partial unique index; it uses `LOCALTIMESTAMP` (to match the `CURRENT_TIMESTAMP` defaults on other rows) and pushes the rows whose `last_pushed_at` equals it. The caller passes the window (`RoomCommentEvent.Window`), so `notify` doesn't read config. `pushToDevices` now takes the text per recipient, since one comment is locked for some readers and not others. `snippet` collapses whitespace to one line and cuts at 120 characters, not bytes; task 6 reuses it for replies. Tests in `internal/notify/roomcomment_test.go`, and checked by breaking the lock comparison, the throttle and the bundle text: each break fails at least one test.
- Task 6: `notifyComment` in `comments.go`, called only when the stored id is the new one (a `client_id` replay returns the old id). The reply and the room notification push side by side, so the request waits one push timeout, not two. A thread author with Replies off isn't sent the `REPLY` and isn't excluded, so they get the comment through their room row, as R2.1 reads ("except anyone notified under R1"). The reply needs the thread author to still be a member (`isRoomMember`). Creators always have a `room_members` row (`CreateRoom` inserts one), so `RoomComment` reaches them. `notify.snippet` is exported as `Snippet` for the reply text. If the username lookup fails, the text says "Someone". Handler tests in `internal/server/notifications_test.go` check the inbox rows each request writes (push isn't configured under test; the pushes are covered in `internal/notify`). Several of task 10's delivery cases are already covered there: reply once, self-reply, Replies off, thread author left, reply at its root's page, retry. Removing the retry guard or the exclusion each fails a test.
- Task 7: `notifyJoin` in `rooms.go`. It notifies only when the insert's `RowsAffected` is 1: two simultaneous joins can both pass the membership check, and the `ON CONFLICT DO NOTHING` one adds nothing. `TestRacingJoinsNotifyOnce` fails 4 runs in 5 without that check. The creator never notifies themselves, though their own join is a 409 anyway. Tests: the creator only, two joins give two rows, 409 / 404 / the creator's own code notify nobody, New members off, racing joins.

- Task 9: sorted on `COALESCE(updated_at, created_at) DESC, id DESC` (the `id` breaks ties between rows written in the same instant). `updated_at` is cast to `timestamptz` like `created_at`.
